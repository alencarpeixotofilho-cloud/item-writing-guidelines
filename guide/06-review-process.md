# 6. Review workflow

Quality is not written into an item; it is **reviewed** into it.

```text
 Author ──► Self-check (itemcheck + checklist) ──► Peer review (content)
    ▲                                                    │
    └──────────── revise ◄── Technical review (form) ◄───┘
                                     │
                                     ▼
                         Approved ──► Item bank ──► Exam ──► Item analysis
                                                                  │
                         revise / retire ◄─────────────────────────┘
```

## 6.1 Stages

1. **Self-check.** The author runs `itemcheck` and the
   [review checklist](../checklist/review-checklist.md).
2. **Content review.** A second content expert answers the item *without* the
   key and confirms that exactly one option is defensible.
3. **Technical review.** A trained reviewer checks form: cues, homogeneity,
   language, blueprint classification.
4. **Decision.** Approve, approve with minor edits, or return with comments.
   Every decision is recorded with the criterion that motivated it.
5. **Post-administration analysis.** Difficulty, discrimination and
   distractor statistics feed back into the item bank
   ([item-analysis-psychometrics](https://github.com/alencarpeixotofilho-cloud/item-analysis-psychometrics)).

## 6.2 Writing useful review comments

* Point to the **criterion**, not the person: *"Lead-in is negatively phrased
  (criterion 6)"*.
* Suggest a **concrete fix** whenever possible.
* Separate **must-fix** issues (wrong key, ambiguity) from **suggestions**.
